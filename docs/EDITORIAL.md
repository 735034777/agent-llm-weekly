# 编辑准则

## 读者与选题

为希望理解并试用 LLM、Agent 前沿技术的研究者与开发者提供每周精选。关注“方法或能力发生了什么变化”，排除融资新闻、无技术细节的宣传、只有 star 增长的项目和重复转载。

优先级依次考虑技术变化、证据质量、读者可用性、时间相关性。关注模型训练与推理，也关注模型外围的执行系统（harness）：提示、工具、上下文、状态保存、恢复和停止条件。新框架数量不等于技术进步。

## 形式与表达

参考 HelloGitHub 的期号、分类、项目链接、短介绍和归档。只借鉴组织形式，不复用其文案、图片或标识。

每期通常 6—10 条，单条约 100—250 字；可以更少，不设置凑数下限。每条包含标题、日期、技术说明、编辑判断、限制和直接来源。标题写清变化，不使用“炸裂”“颠覆”“吊打”等措辞。不为所有栏目强行安排内容。

开头突出本期最值得读的一项，正文按问题分类，结尾给一个可执行的小实验。英文术语首次出现时给出必要中文解释。

## 证据规则

1. 技术事实追溯到论文、作者官网、官方仓库、Release 或评测方法。聚合榜单和社交内容用于发现。
2. 区分首次发布、版本修订、聚合平台收录、评测执行和周报发布日期。只因本周被转发不能成为本周新闻。
3. 研究结果写成“作者报告”或“论文在这些任务中观察到”；核查原文不等于复现。
4. 重要数字同时给出任务、模型、比较基线及预算条件；条件不清楚就省略数字，不自行补全。
5. 不将发布文章等同于已经可用的 API，不将作者开源声明等同于全部资源已逐项核验。
6. 每条必须有局限或适用条件。区分论文明确承认的局限与编辑对证据范围的判断。
7. 重复项目只在有实质变化时再次收录，写明这次改变了什么。同一事件的论文、博客和仓库合并成一条。
8. 旧文进入“长期参考”，设置 `evergreen: true`；不得用旧内容填充新闻栏目。
9. 来源打不开时，记录 `unavailable`；只检查目录或摘要时记录 `partial`。不将未核查写成没有变化。
10. 公开内容不包含本机路径、登录信息、私人材料或完整复制的第三方文章。图片仅在授权明确且有必要时使用。

## 核查等级

- `source-reviewed`：已检查该条直接原始材料，未独立复现。
- `reproduced`：有可追溯的复现实验、条件和结果；仅在确实执行后使用。

每期在 `source_checks` 记录访问状态与范围，正文显示覆盖情况。`reviewed` 只表示完成该来源计划中的检查，不保证穷尽整个网站。

## 更正

修正 `data/issues/NNN.json`，在 `corrections` 中写明日期、原问题和更正；重新生成派生文件。实质更正保留 Git 历史并同步 Release 文案，不悄悄改写既有结论。
